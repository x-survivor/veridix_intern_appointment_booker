# Authentication setup

The login and registration endpoints use the MySQL table named users. The application does not create or migrate the table automatically.

## 1. Create the users table

Select the same database configured by DB_NAME, then execute the SQL in database/users.sql.

The table must contain these columns:

- id: auto-incrementing primary key
- name: account holder name
- email: unique email address
- password_hash: the scrypt password hash generated by the API
- created_at: account creation timestamp

The email column must have a UNIQUE index. The registration endpoint relies on that database constraint to prevent duplicate accounts, including concurrent registration requests.

## 2. Configure the session secret

Add AUTH_SECRET to your local environment file (.env.local). It must contain at least 32 bytes of random secret material. Generate a value with:

    openssl rand -base64 32

Example environment entry (replace the value with your generated secret):

    AUTH_SECRET=your-generated-secret

Keep this value private and do not commit it. Use the same secret across all application instances that need to validate the same sessions.

## 3. Authentication routes

| Method | Endpoint | Purpose |
| --- | --- | --- |
| POST | /api/auth/register | Create an account and sign it in |
| POST | /api/auth/login | Verify credentials and sign in |
| GET | /api/auth/me | Return the currently signed-in user |
| POST | /api/auth/logout | Clear the session cookie |

Registration and login return a signed session in the HttpOnly clinio_session cookie. The cookie uses SameSite=Lax, Secure in production, and a seven-day expiry. Passwords are stored as salted scrypt hashes and are never returned by the API.

## 4. Account fields

Registration accepts a name, email, and password. Email addresses are trimmed and normalized to lowercase. Passwords must contain 8 to 128 characters.

The current authentication flow uses email addresses for sign-in; it does not require a username or role column.
